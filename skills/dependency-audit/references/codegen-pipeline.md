# The codegen toolchain as a supply-chain surface

Some codebases generate their API clients rather than writing them. An OpenAPI spec is the source of truth, and a Go SDK, a TypeScript SDK, and a Terraform provider are generated from it. The reference shape for this pack: a **Huma v2 / go-chi** Go API emits `openapi.json`; **openapi-generator** produces the Go SDK and the Terraform provider; **@hey-api/openapi-ts** produces the TS SDK with a react-query plugin. See `~/projects/glueops/waggle`.

A normal dependency audit scans the manifests and misses this entirely, because the interesting supply-chain surface here is not only the runtime dependencies — it is the **generators**, their **versions**, and the **provenance of the vendored generated code**. Each is a place a compromise or a silent drift enters.

## The generators are dependencies too

Treat every code generator as a build-time dependency with the same scrutiny as a runtime one — more, because it writes code that ships.

- **`@hey-api/openapi-ts`** and its plugins (`@hey-api/client-fetch`, `@hey-api/sdk`, `@tanstack/react-query`) — npm packages, in `devDependencies` or run via `npx`. Pin them. A generator resolved by a floating range means your SDK is generated by whatever version CI happened to fetch, and generated code is code you ship without reading.
- **openapi-generator** — usually invoked as a jar or a Docker image (`openapitools/openapi-generator-cli`). Pin the **exact version**, not `latest`. The `.openapi-generator/VERSION` file records what last ran; confirm it matches what CI invokes. A generator version bump can change auth handling, serialization, or validation in the output without a single line of your code changing.
- **openapitools.json** pins the openapi-generator version for the CLI — check it is set and matches `.openapi-generator/VERSION`. A mismatch means local and CI generate differently.

Report an unpinned or floating generator the same way you would report a missing lockfile: it means the generated code that shipped was never the generated code anyone reviewed.

## Provenance of vendored generated code

Generated SDKs are frequently committed to the repo (`sdk/go`, `sdk/ts`, `ui/src/sdk`) so consumers do not need the toolchain. That vendored code is a supply-chain artifact:

- **Is it reproducible?** Regenerating from the current spec with the pinned generator should produce the committed output with no diff. If it does not, someone hand-edited generated code, or the generator/spec drifted. Both are findings: hand-edits are erased on the next regen (and may be hiding a fix or a backdoor), and drift means the committed client does not match the contract.
- **Was it generated from *your* spec?** Confirm the input is the repo's own `docs/openapi.json`, not a fetched URL. A generator pointed at a remote spec URL pulls a contract you do not control into code you ship — an injection point most audits never look for. In `openapi-ts.config.ts`, `input` should be a local path.
- **Does CI regenerate and fail on drift?** The safe pattern is regenerate-in-CI with a `git diff --exit-code`. Its absence means drift and hand-edits can ship silently; route that gap to `hardening-playbook`.

## Reachability, adjusted for generated code

The reachability triage in `references/supply-chain.md` still applies, with two adjustments:

- **A vulnerable transitive dep inside a generated SDK is reachable if your app calls that SDK path**, even though no hand-written code imports it directly. Trace from your code into the generated client into its dependencies. The generated layer does not break the chain.
- **The generated client's own runtime dependencies** (the fetch client, the react-query runtime, the Go HTTP stack) are yours to audit even though you did not choose them — the generator did. A `@hey-api/client-fetch` advisory is your advisory.

## The Terraform provider is the highest-stakes generated artifact

A generated provider handles credentials and writes state, so its supply-chain and config surface matters more than the SDKs':

- **Provider dependency tree.** openapi-generator Go providers pull the terraform-plugin-framework and an HTTP stack. Audit them; a provider runs wherever `terraform` runs, often in CI with cloud credentials present.
- **Credential-in-state risk** is a config finding, but surface it here too because it is so common in generated providers: Terraform state is plaintext, and a provider that stores the API token in state leaks it into every state backend and CI log. Cross-reference `secure-code-review/references/codegen-pipeline.md`.
- **Generator version pinning matters most here**, because a provider regenerated by a newer openapi-generator can change how it handles auth or TLS between runs, on infrastructure code, silently.

## What to report

- Generators unpinned or on `latest` → same class as a missing lockfile.
- `.openapi-generator/VERSION` ≠ `openapitools.json` ≠ what CI runs → drift risk, generated output is nondeterministic.
- Vendored generated code that does not reproduce from the current spec + pinned generator → hand-edited or drifted; investigate why.
- Generator input that is a remote URL rather than the local spec → an uncontrolled contract entering shipped code.
- No regenerate-and-diff gate in CI → drift and hand-edits can ship; route to `hardening-playbook`.
- Vulnerable dependencies inside vendored SDKs, triaged for reachability through the generated call path.
